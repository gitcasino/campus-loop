# CampusLoop

## Software Requirements Specification

> **Course:** 22AIE205 — Introduction to Python  
> **Project Type:** Data Analytics Web Application Development  
> **Technology Choice:** **Option A — Streamlit + Pandas + NumPy + Plotly/Matplotlib**  
> **Theme:** Campus sharing and circular consumption  
> **SDG Alignment:** SDG 12 — Responsible Consumption and Production  
> **Storage:** CSV files only  
> **Primary Goal:** Build a polished, browser-based campus sharing platform where students can borrow, lend, swap, or give away useful items instead of purchasing new ones.

------------------------------------------------------------------------

## 1. Introduction

### 1.1 Purpose

CampusLoop is a campus resource-sharing platform that helps students
find and share items within their campus community. The platform makes
it easier to borrow, lend, swap, or give away useful items instead of
purchasing new ones unnecessarily.

The system combines resource sharing with data management, analytics,
visualization, and impact tracking.

### 1.2 Problem Statement

Students frequently own items that they use only occasionally, while
other students may need the same items temporarily. This can lead to
unnecessary purchases, underused resources, and avoidable waste.

CampusLoop provides a centralized way for students to discover available
resources and participate in campus-level sharing.

### 1.3 Objectives

CampusLoop aims to:

-   Provide a simple platform for listing items available for sharing.
-   Help students discover items they need.
-   Support borrowing, lending, swapping, and giving away.
-   Maintain structured records of listings and sharing activity.
-   Provide search, filtering, and sorting capabilities.
-   Analyze campus sharing activity using Python data-analysis tools.
-   Visualize useful statistics and trends.
-   Track measurable resource-sharing and sustainability impact.

### 1.4 Scope

The project covers a Python-based interactive web application using CSV
files as its persistent data source.

The application includes item management, discovery, sharing activity,
analytics, visualization, and reporting.

The project does not require a production database, real payment
processing, or a production-grade authentication system.

------------------------------------------------------------------------

## 2. Product Overview

### 2.1 Target Users

The primary users are students within a campus community.

### 2.2 Core Concept

A student should be able to:

1.  Find an item they need.
2.  View its availability and relevant details.
3.  Request or initiate a sharing action.
4.  Share their own unused items with others.
5.  View the activity and impact generated by the platform.

### 2.3 Sharing Modes

CampusLoop supports four primary forms of sharing:

-   **Borrow** --- temporarily use an item owned by another student.
-   **Lend** --- make an owned item available temporarily.
-   **Swap** --- exchange one item for another.
-   **Give Away** --- transfer an unwanted item to another student.

## 3. Functional Requirements

### 3.1 Item Listing Management

The system shall allow users to create item listings containing relevant
information such as:

-   Item name
-   Category
-   Description
-   Sharing mode
-   Availability
-   Location
-   Owner
-   Condition
-   Relevant date information

The system shall allow existing listings to be viewed, modified, and
removed.

### 3.2 Item Discovery

The system shall allow users to:

-   Browse available items.
-   Search by item name or relevant text.
-   Filter by category.
-   Filter by sharing mode.
-   Filter by availability.
-   Filter by location.
-   Sort records using relevant fields.

### 3.3 Sharing Activity

The system shall maintain records of sharing activities associated with
listings.

A sharing record may contain:

-   Item
-   Participants
-   Sharing type
-   Date
-   Status
-   Relevant quantity or duration where applicable

The system shall allow these records to be analyzed and reported.

### 3.4 Smart Matching

CampusLoop shall provide a matching mechanism that identifies
potentially suitable listings for a user's requirements.

Matching may consider factors such as:

-   Item or category compatibility
-   Availability
-   Location
-   Sharing preference
-   Other relevant listing attributes

Matching results shall provide understandable reasons for their
relevance rather than presenting an unexplained result.

### 3.5 User Information

The application shall maintain basic user information needed to
associate listings and sharing activities with users.

The project may use simulated student identities rather than production
authentication.

### 3.6 Impact Tracking

The system shall record measurable indicators associated with resource
sharing.

Examples include:

-   Number of items shared
-   Number of borrowing or exchange activities
-   Items reused
-   Estimated purchases avoided
-   Sharing activity by category
-   Other project-defined sustainability indicators

Impact figures shall be based on available application data and clearly
identified assumptions.

### 3.7 Analytics

The system shall provide analytical views of the available data.

Analytics may include:

-   Total listings
-   Available listings
-   Sharing activity counts
-   Category distribution
-   Sharing-mode distribution
-   Activity trends over time
-   Most active categories
-   Other meaningful statistics derived from stored data

### 3.8 Visualization

The application shall provide dynamic visualizations based on the
current CSV data.

The visualizations shall include at least two different chart types and
shall update according to the available data and selected filters.

### 3.9 Reporting

The system shall provide a summary report for relevant dataset views.

A report shall include, where applicable:

-   Report timestamp
-   Current row count
-   Applied filters
-   Relevant summary statistics
-   Current dataset or activity information

## 4. Data Requirements

### 4.1 Data Storage

CSV files shall be used as the persistent storage mechanism for the
project.

The principal data domains are:

-   Users
-   Item listings
-   Sharing activities
-   Impact information

The final implementation may organize these domains into multiple CSV
files according to the project's academic ownership requirements.

### 4.2 Data Integrity

The system shall:

-   Validate required fields before creating records.
-   Validate expected data types.
-   Prevent duplicate records where uniqueness is required.
-   Handle missing values explicitly.
-   Preserve valid CSV data after modifications.
-   Report invalid operations without exposing raw application errors.

### 4.3 CRUD Operations

The application shall support:

-   **Create:** add a new record after validation.
-   **Read:** view, search, filter, and sort records.
-   **Update:** modify an existing record.
-   **Delete:** remove an existing record after confirmation.

CRUD operations shall operate on the application's CSV data.

------------------------------------------------------------------------

## 5. User Interface Requirements

### 5.1 General Interface

The interface shall provide:

-   Clear navigation.
-   Readable presentation of records.
-   Accessible forms for data entry.
-   Clear feedback after successful operations.
-   Friendly error messages for invalid operations.
-   Responsive presentation across common screen sizes.

### 5.2 Visual Design

CampusLoop shall use a modern, clean visual identity appropriate for a
student-facing digital platform.

The interface may include:

-   Dark and light display modes.
-   Glass-style interface elements.
-   Subtle motion and transitions.
-   Data-focused dashboard components.
-   Consistent typography and spacing.

Visual design shall support usability rather than interfere with access
to data or controls.

------------------------------------------------------------------------

## 6. Error Handling

The application shall handle expected data and user errors without
terminating the application.

The system shall explicitly account for:

-   Missing CSV files.
-   Empty CSV files.
-   Invalid input.
-   Incorrect data types.
-   Invalid record identifiers.
-   Duplicate records.
-   Missing values.
-   Invalid update operations.
-   Invalid delete operations.

Users shall receive understandable messages describing the problem and,
where appropriate, how it can be corrected.

------------------------------------------------------------------------

## 7. Analysis and Visualization Requirements

The project shall demonstrate Python data-analysis capabilities,
including Pandas and/or NumPy.

Each required dataset/page shall provide at least:

-   Three meaningful summary statistics.
-   Two different dynamic chart types.
-   Search, filtering, or sorting of records.
-   Explicit treatment of missing data.

Charts shall be generated from the current CSV data rather than static
images.

The application shall make the selected analysis understandable through
appropriate labels, titles, and supporting information.

## 8. Technical Constraints

The project shall follow the academic technology requirements:

-   Python 3.10 or later.
-   Python-based web framework, with Streamlit as the recommended
    option.
-   CSV files as persistent storage.
-   Pandas and NumPy for data handling and analysis.
-   Matplotlib, Plotly, and/or Seaborn for visualization.
-   A `requirements.txt` file containing project dependencies.
-   Relative paths rather than machine-specific absolute paths.
-   A virtual environment for development.

The complete application shall be runnable after installing the
dependencies listed in `requirements.txt`.

------------------------------------------------------------------------

## 9. Object-Oriented Design

The application shall use object-oriented programming as part of its
implementation.

CRUD logic for the required datasets shall be represented through custom
Python classes rather than relying exclusively on inline data-frame
operations.

The overall codebase shall demonstrate appropriate use of:

-   Classes and objects
-   Methods
-   Encapsulation and/or inheritance
-   Functions and modules
-   Exception handling

The exact class structure is an implementation decision and is not
prescribed by this SRS.

## 12. Success Criteria

CampusLoop will satisfy its functional objectives when it provides:

1.  A working campus resource-sharing interface.
2.  Item listing management with complete CRUD operations.
3.  Search, filtering, and sorting of stored data.
4.  Working CSV persistence.
5.  Meaningful data analysis using Pandas and/or NumPy.
6.  At least two dynamic visualization types for the required datasets.
7.  Robust handling of invalid and missing data.
8.  Summary reporting with timestamp, row count, and applicable filters.
9.  A clear and usable interface.
10. An implementation that can be explained and defended by each student
